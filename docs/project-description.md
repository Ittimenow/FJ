# Financial Journey — описание проекта

## 1. Назначение

Financial Journey — многопользовательская онлайн-версия финансовой настольной
игры «Финансовое путешествие», созданной по мотивам CASHFLOW. Проект помогает
игрокам тренировать управление личными финансами: учитывать доходы и расходы,
покупать и продавать активы, пользоваться кредитами, переживать случайные
финансовые события и стремиться к финансовой свободе.

Приложение объединяет игровое поле, финансовый отчёт игрока, карточки, сделки,
чат и журнал действий в одной синхронизируемой игровой комнате. Сервер является
авторитетным источником состояния партии и самостоятельно проверяет игровые
действия.

## 2. Основные возможности

- регистрация и вход пользователя;
- профиль, аватар, история партий и агрегированная статистика;
- создание комнаты и присоединение по коду;
- партии для 2–6 игроков;
- роли игрока, банкира и наблюдателя;
- выбор уникальной фишки;
- бросок кубика и движение по малому и большому кругу;
- начисление зарплаты и изменение финансового состояния;
- карточки сделок, рынка, расходов и других игровых событий;
- покупка и продажа активов;
- банковские кредиты, погашение долгов и банкротство;
- переход из «Крысиных бегов» на «Скоростную дорожку»;
- синхронизация комнаты, чата и журнала действий в реальном времени;
- обратная связь от пользователей;
- административное управление пользователями, карточками, обратной связью и
  журналом изменений;
- защищённый экспорт истории партий для аналитики и воспроизведения.

Полные правила игры и разбор спорных ситуаций находятся в
[руководстве пользователя](user-guide.md).

## 3. Игровая модель

### 3.1. Цель

На малом круге игрок стремится создать пассивный доход, превышающий его
ежемесячные расходы. После этого он переходит на большой круг, где может
победить, достигнув установленной игрой финансовой цели или купив свою мечту.

### 3.2. Финансы игрока

Для каждого участника хранятся наличные, доходы, расходы, пассивный доход,
денежный поток, количество детей, активы, обязательства и статус банкротства.
Финансовое состояние изменяется только через проверенные сервером игровые
операции.

Несмотря на исторические имена полей вида `*_cents`, денежные значения
интерпретируются как прямые игровые суммы: значение `500` означает `$500`, а не
`50000` центов.

### 3.3. Карточки

Карточка состоит из отображаемого текста, метаданных, условий и
структурированных эффектов. Backend применяет эффекты универсальным механизмом,
без отдельного программного кода для каждой карточки.

Поддерживаются изменения наличных и денежного потока, создание обязательств,
дробление и консолидация акций, а также обнуление актива. Обязательные расходы
применяются автоматически, а от покупаемой сделки игрок может отказаться.
Техническое описание формата приведено в документе
[«Модульные действия карточек»](card-actions.md).

## 4. Архитектура

Проект организован как npm-монорепозиторий:

```text
Браузер
  ├─ HTTP ───────────────► Next.js web
  ├─ REST API ───────────► NestJS API ─────► PostgreSQL
  └─ Socket.IO ──────────► NestJS API ─────► Redis (опционально)
                                      └────► SMTP (почтовые уведомления)
```

### 4.1. Web-приложение

Frontend находится в `apps/web` и построен на Next.js 15, React 19 и
TypeScript. Для аутентификации используется NextAuth с Credentials-провайдером,
для realtime-связи — Socket.IO Client, для оформления — Tailwind CSS.

Основные страницы:

| Маршрут | Назначение |
| --- | --- |
| `/` | входная точка приложения |
| `/login` | вход |
| `/register` | регистрация |
| `/dashboard` | список и создание партий |
| `/join/[code]` | присоединение к комнате по коду |
| `/games/[id]` | игровая комната |
| `/profile` | профиль и статистика |
| `/guide` | правила игры |

### 4.2. API

Backend находится в `apps/api` и построен на NestJS и TypeScript. Он отвечает за:

- регистрацию, вход, JWT и проверку ролей;
- пользователей и профили;
- создание партий и управление участниками;
- игровую логику и финансовые операции;
- карточки, сделки, рынок и банкротство;
- чат и realtime-события;
- обратную связь;
- административные операции и аналитические выгрузки.

HTTP API по умолчанию доступен на порту `4000`. Web-приложение в режиме
разработки работает на порту `3000`.

### 4.3. Общая игровая логика

Пакет `packages/shared` содержит типы, события, описание игрового поля, фишки и
части игрового движка, которые используются frontend и backend. Это уменьшает
расхождения между отображением состояния в браузере и серверными правилами.

### 4.4. База данных

Пакет `packages/database` содержит Prisma-схему, клиент базы и seed-скрипт.
Основные группы сущностей:

- пользователи и роли;
- партии и участники;
- профессии и строки стартового финансового отчёта;
- карточки, метаданные, условия и эффекты;
- текущее финансовое состояние игрока;
- активы и обязательства;
- игровые события и сообщения чата;
- пользовательская обратная связь.

PostgreSQL является основным постоянным хранилищем.

### 4.5. Event sourcing

Проект использует комбинированный подход:

- актуальное состояние хранится в отдельных таблицах для быстрых запросов;
- каждое значимое действие партии записывается в `game_events`;
- событие содержит тип, данные действия и при необходимости снимок состояния.

Журнал событий обеспечивает аудит партии, аналитический экспорт,
последовательное воспроизведение и основу для восстановления состояния.

Администратору доступны read-only маршруты аналитики:

```text
GET /api/admin/analytics/games
GET /api/admin/analytics/games/:id
GET /api/admin/analytics/games/:id/replay
GET /api/admin/analytics/export.ndjson
```

Подробности формата находятся в
[описании экспорта аналитики](analytics-export.md).

### 4.6. Realtime и Redis

Socket.IO синхронизирует игровую комнату, чат и журнал действий без ручного
обновления страницы. Redis используется адаптером Socket.IO при работе
нескольких экземпляров API. Для одного экземпляра приложения Redis
необязателен.

## 5. Структура репозитория

| Путь | Содержимое |
| --- | --- |
| `apps/web` | Next.js frontend |
| `apps/api` | NestJS API и игровая логика |
| `packages/shared` | общие типы, события, поле и игровой движок |
| `packages/database` | Prisma-схема, клиент и наполнение справочников |
| `docs` | пользовательская, техническая и эксплуатационная документация |
| `deploy` | конфигурация reverse proxy |
| `scripts` | локальный запуск, production-старт, релизы и проверки |
| `dist` | подготовленные данные профессий и карточек |
| `distr` | неизменяемые входные файлы, переданные пользователем для обработки |
| `reports` | сформированные отчёты и выгрузки |

Файлы в `distr` считаются исходными материалами. Их нельзя изменять,
перезаписывать, форматировать, удалять или переносить; результаты обработки
сохраняются в других каталогах проекта.

## 7. Локальный запуск

### 7.1. Подготовка

```bash
cp .env.example .env
docker compose up -d
npm install
npm run db:generate
npm run db:migrate
npm run db:seed
```

### 7.2. Запуск приложений

В отдельных терминалах:

```bash
npm run dev:api
npm run dev:web
```

После запуска:

- Web: `http://localhost:3000`;
- API: `http://localhost:4000`;
- PostgreSQL: `localhost:5432`;
- Redis: `localhost:6379`.

Альтернативно `npm run dev:local` подготавливает локальные сервисы, Prisma и
справочники, после чего запускает API и Web.

### 7.3. Основные переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | подключение к PostgreSQL |
| `REDIS_URL` | подключение к Redis; необязательно для одного инстанса |
| `JWT_SECRET` | подпись API-токенов |
| `JWT_EXPIRES_IN` | срок жизни API-токена |
| `AUTH_SECRET` | секрет NextAuth |
| `NEXTAUTH_URL` | публичный адрес web-приложения |
| `API_PORT` | порт NestJS API |
| `API_URL` | серверный адрес API для frontend |
| `NEXT_PUBLIC_API_URL` | адрес API, доступный браузеру |
| `WEB_ORIGIN` | разрешённый origin frontend |

Секреты из примера окружения нельзя использовать в production.

## 8. Данные и наполнение справочников

Seed-скрипт импортирует профессии и карточки из:

- `dist/seed_professions.sql`;
- `dist/seed_cards.sql`.

Эти SQL-файлы остаются внешним источником справочных данных. Приложение не
зависит от MySQL DDL: seed-скрипт разбирает `INSERT`-операторы и записывает
данные через Prisma в PostgreSQL.

Команды управления:

```bash
npm run db:generate
npm run db:migrate
npm run db:push
npm run db:seed
npm run db:sync-cards
```

`db:seed` используется для первичного наполнения, а `db:sync-cards` — для
синхронизации карточек с актуальным источником.

## 9. Проверка качества

Основные команды проекта:

```bash
npm run build
npm run typecheck
npm run test
npm run changes:check
```

- `build` собирает рабочие пространства;
- `typecheck` проверяет типы TypeScript;
- `test` запускает доступные модульные тесты;
- `changes:check` проверяет структуру пользовательского журнала изменений.

Любая доработка, влияющая на поведение или интерфейс, должна сопровождаться
записью в `docs/changes.json` в релизе `unreleased`.

## 10. Развёртывание

### 10.1. Timeweb Cloud App Platform

Docker-образ запускает NestJS API и Next.js как два внутренних процесса.
Встроенный proxy публикует единый порт `3000`: запросы к backend и Socket.IO
направляются в API, остальные — в web-приложение. Проверка готовности доступна
по `/healthz`.

Пошаговая инструкция и production-переменные:
[деплой в Timeweb Cloud App Platform](deploy-timeweb.md).

### 10.2. Timeweb Cloud Server / VPS

На VPS Caddy принимает HTTP/HTTPS-трафик, приложение и PostgreSQL работают в
Docker, а данные базы сохраняются в постоянном volume. Redis подключается
отдельным Docker Compose profile, если приложение масштабируется на несколько
инстансов.

Инструкция по первому запуску, обновлению и резервному копированию:
[деплой на Timeweb Cloud Server](deploy-timeweb-vps.md).
