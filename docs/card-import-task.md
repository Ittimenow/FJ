# Задание для ChatGPT: импорт новых игровых карточек в базу

Ниже приведено полное задание. Выполняй его как инженер, работающий с репозиторием проекта Financial Journey.

## Роль и цель

Нужно обработать приложенные исходные материалы с новыми игровыми карточками, привести карточки к структуре проекта, проверить их игровые правила и подготовить безопасный импорт в PostgreSQL.

Результат должен быть пригоден для реального использования в проекте, а повторный импорт тех же данных не должен создавать дубликаты или повреждать уже существующие карточки.

## Порядок работы

1. Сначала прочитай `AGENTS.md` и соблюдай его требования.
2. Изучи приложенные файлы с новыми карточками и связанные файлы проекта.
3. Не изменяй, не перезаписывай, не форматируй, не удаляй и не перемещай файлы из `distr/`. Это неизменяемые исходники.
4. До реализации покажи краткий план, перечисли предполагаемые изменения и способы проверки. Дождись явного подтверждения пользователя.
5. После подтверждения нормализуй данные, реализуй или используй безопасный способ импорта и выполни проверки.
6. Не подключайся к production и не изменяй production-базу без отдельного явного разрешения пользователя.

Если исходные карточки или репозиторий не приложены, сначала сообщи, каких файлов не хватает. Не придумывай содержимое отсутствующих карточек.

## Каноническая структура карточки

Для подготовки данных используй следующий логический JSON-формат:

```json
{
  "cardType": "SMALL_DEAL",
  "slug": "small_deal_custom_001",
  "title": "Название карточки",
  "bodyText": "Полный текст карточки",
  "category": "realestate",
  "subcategory": null,
  "isActive": true,
  "meta": [
    {
      "metaKey": "price",
      "metaValue": "50000"
    }
  ],
  "effects": [
    {
      "effectType": "cash.adjust",
      "amountCents": -5000,
      "payload": {}
    }
  ],
  "conditions": [
    {
      "condType": "has_children",
      "payload": {}
    }
  ]
}
```

Поля `id`, `createdAt`, `updatedAt` и идентификаторы строк `meta`, `effects`, `conditions` при создании не передаются: их создаёт база.

### Основные поля

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `cardType` | обязательно | Тип колоды из списка ниже |
| `slug` | обязательно | Уникальный и стабильный технический идентификатор |
| `title` | обязательно | Название для игрока и журнала, максимум 240 символов |
| `bodyText` | обязательно | Полный текст карточки, максимум 4000 символов |
| `category` | опционально | Категория карточки или тип создаваемого актива |
| `subcategory` | опционально | Дополнительная классификация |
| `isActive` | опционально | По умолчанию `true`; в случайную выдачу попадают только активные карточки |
| `meta` | опционально | Параметры сделки или актива |
| `effects` | опционально | Структурированные игровые действия |
| `conditions` | опционально | Условия выполнения эффектов |

Допустимые значения `cardType` в JSON и административном API:

- `SMALL_DEAL` — малая сделка;
- `BIG_DEAL` — крупная сделка;
- `MARKET` — рынок и продажа активов;
- `DOODAD` — обязательный расход;
- `FAST_TRACK` — карточка быстрой дорожки;
- `DREAM` — мечта.

В старом SQL seed эти значения записываются в нижнем регистре: `small_deal`, `big_deal`, `market`, `doodad`, `fast_track`, `dream`.

## Денежные значения

Несмотря на технические имена `amountCents`, `balanceCents`, `paymentCents` и другие поля с суффиксом `Cents`, текущие данные используют прямые игровые денежные суммы.

Примеры:

- `500` означает `$500`;
- `-500` означает списание `$500`;
- `17000` означает долг `$17 000`.

Не умножай суммы на 100. Проверь это правило по актуальному коду и существующим данным перед импортом.

## Метаданные `meta`

`meta` — массив уникальных пар ключ-значение. В пределах одной карточки один `metaKey` не должен повторяться. Все `metaValue` хранятся как строки.

| `metaKey` | Назначение |
| --- | --- |
| `symbol` | Тикер акции или фонда; необходим для операций с количеством акций |
| `today_price` | Текущая цена одной акции |
| `price` | Полная цена актива или цена продажи по карточке рынка |
| `price_min` | Справочная минимальная цена акции |
| `price_max` | Справочная максимальная цена акции |
| `down_payment` | Первоначальный взнос |
| `mortgage` | Остаток ипотеки или закладной |
| `cashflow_monthly` | Ежемесячный денежный поток актива |
| `per_child` | При `true`, `1` или `yes` денежный эффект умножается на количество детей |
| `liability_added` | Legacy-поле; само по себе долг не создаёт |

Для недвижимости обычно нужны `price`, `down_payment`, `mortgage`, `cashflow_monthly`. Для акции — `symbol`, `today_price`, `price`; при наличии указываются `price_min` и `price_max`.

Не добавляй произвольные ключи, рассчитывая, что игра начнёт их обрабатывать. Новый ключ требует проверки использования в игровом движке.

## Эффекты `effects`

Для новых карточек используй канонические типы:

| `effectType` | Значение `amountCents` | Результат |
| --- | ---: | --- |
| `cash.adjust` | денежная сумма | Плюс добавляет наличные, минус списывает |
| `cashflow.adjust` | денежная сумма | Плюс добавляет пассивный доход, минус увеличивает ежемесячные расходы |
| `liability.create` | сумма долга | Создаёт пассив игрока |
| `asset.quantity.multiply` | коэффициент | Умножает количество акций с указанным `meta.symbol` |
| `asset.quantity.divide` | коэффициент | Делит количество акций с указанным `meta.symbol` |
| `asset.wipeout` | обычно `0` | Обнуляет подходящие акции и закрывает актив |

Поддерживаемые legacy-названия встречаются в старых данных, но не должны использоваться для новых карточек без необходимости:

- `cash_delta` → `cash.adjust`;
- `conditional_cash_delta` → `cash.adjust`;
- `cashflow_delta` → `cashflow.adjust`;
- `stock_split` → `asset.quantity.multiply`;
- `stock_reverse_split` → `asset.quantity.divide`;
- `stock_wipeout` → `asset.wipeout`.

### `payload` эффекта

```json
{
  "automatic": true,
  "mandatory": true,
  "type": "doodad_loan",
  "name": "Название долга",
  "balanceCents": 17000,
  "paymentCents": 340
}
```

Поддерживаемые параметры:

- `automatic: true` или `mode: "automatic"` — выполнить эффект при выпадении карточки;
- `mandatory: true` или `required: true` — обязательное действие;
- `type` — тип создаваемого долга;
- `name` — название долга, по умолчанию используется заголовок карточки;
- `balanceCents` — сумма долга, если она не задана через `amountCents`;
- `paymentCents` — ежемесячный платёж по долгу.

Операции с акциями выполняются автоматически и требуют `meta.symbol`.

У покупаемых `SMALL_DEAL` и `BIG_DEAL` неавтоматические `cash.adjust` и `cashflow.adjust` используются как параметры покупки: денежный эффект определяет первоначальный взнос, а эффект денежного потока — cashflow создаваемого актива.

Для `DOODAD` обязательные расходы должны быть выражены через `cash.adjust`, `cashflow.adjust` и/или `liability.create`. Не полагайся только на текст карточки.

Не создавай новый `effectType`, пока для него не реализованы обработка в игровом движке, валидация и тесты.

## Условия `conditions`

Поддерживаются:

| `condType` | Проверка |
| --- | --- |
| `has_children` | У игрока есть хотя бы один ребёнок |
| `has_rental_realestate` | У игрока есть актив сдаваемой недвижимости |
| `has_8_plex` | У игрока есть актив восьмиквартирного дома |

Если условий несколько, должны выполняться все. `payload` этих условий в текущей реализации не используется.

Неизвестный `condType` должен считаться ошибкой импорта. Не импортируй его как строку без реализации: игровой движок может фактически пропустить неизвестное условие.

## Нормализация исходных карточек

Для каждой входной карточки:

1. Сохрани смысл и полный пользовательский текст.
2. Исправляй только очевидные ошибки распознавания после проверки по источнику.
3. Создай уникальный стабильный `slug` в нижнем регистре. Не меняй `slug` существующей карточки без причины.
4. Определи `cardType`, `category` и `subcategory`.
5. Вынеси цены, первоначальный взнос, ипотеку, cashflow и тикер в `meta`.
6. Перенеси любое изменение финансового состояния в `effects`.
7. Добавь `conditions`, если действие зависит от активов, детей или другого поддерживаемого состояния.
8. Сверь текст карточки со структурированными значениями. Суммы и правила не должны противоречить друг другу.
9. Если механику нельзя выразить существующей схемой, не имитируй её неподходящим эффектом. Пометь карточку как требующую новой игровой механики и опиши необходимое изменение.

Особенно внимательно проверяй `MARKET`: часть рыночной логики сейчас распознаёт актив по тексту и поддерживает не все сценарии. Для новой рыночной карточки докажи профильным тестом, что она находит правильный актив и верно считает сумму продажи за вычетом ипотеки.

## Требования к безопасному импорту

1. Сначала валидировать весь набор без записи в базу.
2. Проверить обязательные поля, допустимые типы, длины строк и формат JSON.
3. Проверить уникальность `slug` во входном наборе и отсутствие повторов `metaKey` внутри карточки.
4. Отклонять неподдерживаемые `effectType` и `condType`.
5. Проверять, что обязательные параметры механики присутствуют: например, `meta.symbol` для операций с акциями.
6. Поддержать режим `dry-run`, который ничего не записывает.
7. Выполнять фактическую запись транзакционно.
8. Создавать или обновлять карточки по `slug`.
9. При обновлении заменять `meta`, `effects`, `conditions` только у карточек из входного набора.
10. Не удалять, не деактивировать и не изменять остальные карточки.
11. Повторный импорт того же набора не должен создавать дубликаты.
12. После выполнения вывести отчёт: создано, обновлено, без изменений, отклонено.

Для небольшого набора можно использовать существующий административный API `POST /admin/cards` и `PATCH /admin/cards/:id`, если это действительно безопаснее и доступна авторизация администратора.

Для массового импорта подготовь отдельный проверяемый импортёр с `dry-run`. Не используй `npm run db:seed` на рабочей базе: обычный seed удаляет все карточки перед загрузкой. Не полагайся без проверки на `npm run db:sync-cards`: текущая команда связана с одноразовой миграцией и после её применения может завершиться без импорта новых данных.

## Проверка результата

До импорта зафиксируй количество карточек и связанных записей. После импорта:

1. Сверь количество созданных и обновлённых карточек с отчётом.
2. Выборочно прочитай карточки из базы вместе с `meta`, `effects`, `conditions`.
3. Повтори импорт и докажи идемпотентность.
4. Проверь, что старые карточки, отсутствующие во входном наборе, не изменились.
5. Добавь или обнови тесты как минимум для представленных механик:
   - покупка обычной сделки;
   - покупка акции;
   - обязательный расход;
   - условный эффект;
   - создание долга;
   - изменение количества акций;
   - продажа по карточке `MARKET`, если такие карточки импортируются.
6. Выполни профильные тесты, `npm run typecheck` и `npm run changes:check`.
7. Если изменение влияет на доступные карточки, интерфейс или поведение игры, добавь короткую пользовательскую запись в `docs/changes.json`, релиз `unreleased`.

## Формат результата

В конце работы предоставь:

1. Краткое резюме выполненного.
2. Список новых, обновлённых и отклонённых карточек.
3. Путь к нормализованному файлу с карточками.
4. Путь к импортёру или использованный API-процесс.
5. Команду `dry-run`.
6. Команду фактического импорта, но не запускай её на production без отдельного разрешения.
7. Результаты тестов и проверок.
8. Список карточек, которым нужна ещё не реализованная игровая механика.
9. Все сделанные предположения и найденные расхождения между текстом карточек и структурированными данными.

Главный критерий приёмки: новые карточки корректно представлены в структуре проекта и могут быть безопасно импортированы повторно без удаления, дублирования или незаметного изменения существующих данных.
